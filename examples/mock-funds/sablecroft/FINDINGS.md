# Sablecroft Alternatives: what did not fit the platform

Evidence tags: **measured** means a test in `tests/mock_funds/test_sablecroft.py` or a command run for this
drill shows it; **inferred** means read from code or docs, or from how the real service behaves, and not run.
"Generic" means it belongs in the platform or Quant Toolbox; "fund" means it is rightly the fund's own.

## Fund of funds and private markets

| # | Area | What happened (evidence) | Severity | Generic platform fix suggested | Fund-specific or generic |
| --- | --- | --- | --- | --- | --- |
| 1 | Analytics: smoothed returns | `analyze_performance` on IC01 (planted 1.6x smoothing) gives Sharpe 2.71 and probabilistic Sharpe 0.99999, with no autocorrelation warning (measured). The Lo-adjusted Sharpe is 1.21. | major | Add lag-1..k autocorrelation, Lo-adjusted Sharpe, and a smoothing flag to the performance output; put unsmoothing and Lo in Quant Toolbox. | Generic (the GLM fit is a fund choice) |
| 2 | Analytics: unsmoothing quality | My method-of-moments MA(2) fit lands within 20% of the planted ratio on the two smoothed managers (1.71 vs 1.54 sample) but reads liquid EQ01 as 1.26x smoothed (measured). | minor | If Toolbox ships it, include the maximum-likelihood fit and a significance test, not only point weights. | Generic |
| 3 | Analytics: private markets | Platform has no XIRR, TVPI/DPI/RVPI, or PME. | 4 | Analytics: Long-Nickels | When distributions exceed what the calls would have bought in the index, the replicating terminal value is negative and the LN IRR is undefined. 3 of 12 funds hit it (measured). | minor | Toolbox should return "undefined" with a reason, not a number. | Generic |
| 5 | Frequency: lagged and revised returns | The platform has no vintage concept. | 6 | Frequency: point-in-time | The store serves the latest cut only. | 11 | Data shape: sparse dated series | A private fund's cash flows are 3 to 30 dated amounts in an index of 369 dates; the other cells are NaN. | 14 | Calendar | `liquidity_ladder` needs month/quarter/year-end dealing dates, notice periods, lock-up ends: calendar logic written by hand (measured). | minor | Business-day and dealing-calendar helpers in Toolbox. | Generic (the ladder itself is the fund's) |
| 15 | Signal tools | `analyze_signal` and `run_backtest` run on 22 managers, 58 months (measured: ok), but horizons default to 1, 5, 21 periods, i.e. 21 months, and rank IC across funds mostly reflects market beta. | 18 | Acceptance | `run_acceptance` paths cannot index a list: `rows.0.t_stat` fails with "no number at" (measured); the top revision-bias row cannot be asserted. Only absolute tolerance. | minor | Allow `rows[0].t_stat` or `rows.0.t_stat`; allow string/boolean expectations. | Generic |
| 19 | Acceptance: retrieval | Intuitive questions fail: "smoothed returns and unsmoothed volatility of illiquid managers" returns only the IC minutes, not the dedicated note; "administrator statement format change" (the note's own title) abstains; "Getmansky Lo Makarov weights true volatility" works (measured). | # | Area | What happened (evidence) | Severity | Generic platform fix suggested | Fund-specific or generic |

## Data connection

Lines of code in my store (`sablecroft_store.py`, `sablecroft_warehouse.py`, `sablecroft_views.sql`; non-blank, non-comment; measured by a line count):

| Part | Lines | Would be generic? |

| Query and mapping (declarative `ENTRIES`: id, SQL, shape, params; strategy splits generated in a loop) | 39 | The mechanism is generic; the SQL text is the fund's |
| Serving views in Databricks SQL | 74 | Fund-specific (conventions: best-of-vintage, FX, signs) |
| Pivot and shape (`_wide`, `_csv`, null to NaN) | 16 | Yes |

Would a generic SQL-backed `DatasetStore` (one query per dataset id, long rows pivoted to wide) have replaced my adapter? Yes for about 80 lines: connection, mapping, pivot, caching, and version would all be the platform's, leaving only the SQL and its conventions. It needs: bound parameters per entry (the strategy filter), a "table" shape beside "long", NaN for NULL, a data-version hook (Delta version or ETag), refusing duplicate (date, key) rows (finding 12), and typed non-numeric columns (finding 10). Kestrel's pilot adapter has the same structure (inferred from reading `warehouse_store.py`).

Dialect differences met:
- **Three-part names**: Unity Catalog's `sablecroft.curated.x` works in DuckDB after `ATTACH ':memory:' AS sablecroft` (measured). My first stand-in, SQLite, has no three-part names; I had to rewrite names with a regex, then dropped it.
- **Parameters**: DuckDB uses `?`; `databricks-sql-connector` uses native `:name` markers (or `%(name)s` in older versions), SQLAlchemy dialects use their own style (inferred). The store must not hard-code one.
- **Identifier case**: both are case-insensitive for unquoted names; columns named `date`, `return`, `level`, `value` needed no quoting in DuckDB (measured); reserved-word rules differ in Databricks (inferred).
- **Date types**: the curated Parquet holds ISO strings (as the raw landing files do); a real Delta table holds `DATE`, which the connector returns as `datetime.date`, and `TIMESTAMP` would print with a time part (inferred). The store `str()`s the first column.
- **Hive partitions**: DuckDB adds `dt`, `year`, `fund_id` from the folder name with `hive_partitioning`; `pm_cashflows.fund_id` exists only because of that (measured). Delta stores partition values in the log instead.
- **Window functions** (`SUM() OVER`) and `CREATE OR REPLACE VIEW` ran unchanged in DuckDB (measured); `QUALIFY` and time travel I did not use.

## Not a platform gap (rightly the fund's)

IRR/PME conventions, the unsmoothing profile, the ladder's gate and payout assumptions, the choice of `ret_best`, FX conversion, and the strategy codes are the fund's own tools and views; only the missing building blocks in 3, 5, 7, 10, 13, and the identity and run-store items are generic.
