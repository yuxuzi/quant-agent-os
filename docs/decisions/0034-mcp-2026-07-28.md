# 0034: Serve MCP 2026-07-28 and the revisions before it, on the MCP SDK 2

- Status: proposed for 1.0; amends [0002](0002-mcp-boundary.md) and [0012](0012-remote-mcp-over-http.md), and
  answers open question O-2
- Date: 2026-11-23

## Context

The MCP specification's 2026-07-28 revision removed the `initialize` handshake and the `Mcp-Session-Id`
header: each request carries its own protocol version and context, and a client discovers a server with
`server/discover`. The Python SDK shipped 2.0 with it on 2026-07-28; 2.3.0 followed on 2026-10-02. SDK 1.x
is still patched (1.30.0, 2026-09-07) but speaks only the handshake revisions, up to 2025-11-25.

Until now the platform pinned `mcp>=1.20,<2`. A 1.0 that serves only the older revision would ask every
evaluating firm to trust that its clients keep speaking it. Claude, VS Code, and other hosts are adopting
2026-07-28, and the specification calls 2025-11-25 and earlier "legacy" without giving them an end date.

## Decision

- **Depend on `mcp>=2.3,<3`.** A v2 server answers both eras from one endpoint: the 2026-07-28 request
  path and the `initialize` handshake of 2025-11-25 and earlier. Nothing the operator configures changes.
- **The adapter stays an adapter** (decision 0002). `build_server` passes its handlers to the SDK's
  `Server` constructor rather than decorating them, and reads the HTTP request from each handler's
  context instead of a global. The handlers are the same for both eras.
- **A refused tool call is still a result.** SDK 2 sends a handler's exception as a protocol error; a
  call whose credential lacks `tools:call` keeps returning an error result with the refusal's text, as it
  has since 0.1, so a client can show it. Every other refusal already comes from the executor as a result.
- **Both eras are tested.** Every in-process contract check in `tests/contract/test_mcp_server.py` runs
  over the 2025-11-25 handshake and over 2026-07-28, and the two answers must be equal, apart from the
  server-information stamp that only 2026-07-28 adds. `tests/contract/test_mcp_http.py` and
  `tests/server/test_platform_stdio.py` check that a client which negotiates finds 2026-07-28 over HTTP
  and over stdio, and gets the same tools, results, and refusals as a 2025-11-25 client.
- **`httpx2` replaces `httpx`.** SDK 2 depends on `httpx2`, Pydantic's continuation of HTTPX with the
  same API, and no longer brings `httpx`. The sign-in code and the tests use `httpx2`, so the change
  adds no package the server did not already install. The supply-chain cool-off holds: `httpx2` and
  `httpcore2` lock 2.16.0, since 2.16.2 was a week old.

## Consequences

- The agent-efficiency measure does not change: the tool definitions and results a client reads are
  byte for byte the same.
- A firm's own code that imported the SDK directly (none of the documented interfaces need it) follows
  the SDK's own migration guide.
- The 2026-07-28 features the platform does not use yet, such as cache hints, MCP Apps, and the input
  requests that replace server-initiated elicitation, can be added without another SDK change. Approvals
  still use a URL elicitation error, which both eras accept.
- Revisit when the specification gives the handshake revisions an end date, or SDK 3 appears.
