# 0035: What 1.0 promises

- Status: accepted for 1.0, on the owner's release decision of 2026-11-24; reinstates the deprecation rule
  of [decision 0015](0015-metering-quotas-and-entitlements.md), section 3, which the owner suspended on
  2026-11-04 until the project was mature
- Date: 2026-11-24

## Context

Before 1.0 any release could change anything, and several did. A fund that adopts the platform writes code
and files against it: its own server, its tools, its access rules, its acceptance cases, and the generated
applications it owns. It needs to know which of those survive an upgrade unchanged, and how it will hear
about a change before it lands.

## Decision

From 1.0.0 the platform follows semantic versioning over the surfaces below. A minor release only adds; a
patch release only fixes; anything that breaks one of them waits for a major release.

| Surface | What is promised | Held by |
| --- | --- | --- |
| Served tools | Each tool's name, input schema, output schema, and the meaning of its result, under its own semver ([decision 0015](0015-metering-quotas-and-entitlements.md)) | `scripts/tool-versions.lock`, `tests/server/test_tool_lock.py` |
| A firm's Python | The names in `__all__` of `quant_platform`, `quant_agent_os.registration`, `quant_agent_os.testing`, `quant_agent_os.tools`, and `quant_agent_os.data`, with their signatures | `tests/contract/public_api.lock.json`, `tests/contract/test_public_api.py` |
| Quant Toolbox | The names in its API lock, under the toolbox's own version | `packages/quant-toolbox/tests/api.lock.json` |
| Files a firm writes | The keys file, the access file, the sign-in file, acceptance cases, App Factory specs, and their meaning | Their tests and the [configuration](../configuration.md) reference |
| Settings | Every `QUANT_AGENT_OS_*` environment variable and the `NAME_FILE` convention | [Configuration](../configuration.md) |
| Commands | `qaos` commands and options, and their exit codes | `tests/contract/test_docs.py` for the taught ones |
| HTTP | `/mcp`, `/v1` routes and response shapes, `/healthz`, `/readyz` | `tests/contract` |
| Records | The run store upgrades in place; `qaos runs export` and `qaos runs report` keep their fields | Run store tests and the upgrade drill |
| MCP | The protocol revisions served at 1.0.0, 2025-11-25 and 2026-07-28 ([decision 0034](0034-mcp-2026-07-28.md)) | Contract tests in both |

**Not promised:** anything else, including names that begin with an underscore, modules not listed, the
wording of messages, warnings, notes, and instructions, the skills' text, the template packs (they carry
their own versions, and generated applications belong to the firm), the examples and mock funds, and speed.

**How a change is made:**

- **Deprecation (0015's rule, reinstated).** A breaking change ships first as an addition: a new tool name,
  a new option, or a new name, beside the old one. The old one is marked deprecated in the changelog, in
  `qaos://server/info` for a tool, and in its docstring or help, naming its replacement and a removal no
  earlier than 90 days and one minor release later. Removal is a major release.
- **Security.** A fix that must close a hole now may break a surface in a minor or patch release. The
  changelog says so first and plainly.
- **Python and protocols.** Dropping a Python version, or an MCP revision a supported client still uses, is
  announced one minor release ahead and lands in a minor release, because the platform cannot keep either
  past its upstream end of life.

## Consequences

- An upgrade within 1.x needs no change to a fund's server, tools, files, or settings.
- Every public change now costs a lock update and a changelog entry, which is the point.
- Wording stays free to improve, so a firm's own tests should not match messages exactly.
